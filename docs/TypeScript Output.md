# TypeScript Output

## Purpose

Rust emits typed content data, not HTML strings and not one handwritten-style React page per Markdown file. A stable TypeScript runtime converts this data into React components.

This boundary provides:

- Compile-time validation with `satisfies`.
- No Markdown parsing in Node.js or the browser.
- A replaceable visual layer.
- Static route discovery for Next.js.
- Structured content for navigation, search, RSS, sitemaps, and future renderers.
- Diagnostics before `next build` begins.

## Generated directory

The default generated structure is:

```text
src/generated/mambo/
├── manifest.ts
├── navigation.ts
├── search.ts
├── pages/
│   ├── p_01h....ts
│   ├── p_02a....ts
│   └── index.ts
└── build-info.ts
```

Copied assets are separate:

```text
public/mambo/
├── a_<content-hash>.png
├── a_<content-hash>.woff2
└── a_<content-hash>.pdf
```

Every generated file begins with a clear “generated by MamboSite; do not edit” comment and records the schema version. Output paths must be stable across operating systems.

## Stable identifiers

Each page receives a stable `PageId` derived from its site entry, logical source path, and mount identity—not from an absolute path or array position. Human-readable routes are stored separately.

Requirements:

- The same source and mount configuration produce the same ID.
- Renaming or remounting a source may change its ID and route.
- Editing body content does not change its ID.
- IDs contain only safe ASCII characters.
- Asset IDs derive from content hashes so identical assets may be deduplicated.

Generated filenames use IDs rather than titles to avoid Unicode, case, and path-length problems.

## Runtime type contract

The runtime package owns public TypeScript interfaces. The following is representative rather than final implementation syntax:

```ts
export type PageId = string & { readonly __pageId: unique symbol };
export type AssetId = string & { readonly __assetId: unique symbol };

export interface SourceLocation {
  path: string;
  start: { line: number; column: number };
  end: { line: number; column: number };
}

export interface PageRecord {
  schemaVersion: number;
  id: PageId;
  route: string;
  sourcePath: string;
  title: string;
  description?: string;
  status: "published" | "draft";
  listed: boolean;
  date?: string;
  updated?: string;
  tags: readonly TagRef[];
  aliases: readonly string[];
  order?: number;
  cover?: AssetRef;
  data: Readonly<Record<string, JsonValue>>;
  headings: readonly HeadingRecord[];
  body: readonly BlockNode[];
  children: readonly PageId[];
  outgoingLinks: readonly ResolvedLink[];
  backlinks: readonly PageId[];
  assets: readonly AssetRef[];
}
```

`sourcePath` is a normalized path relative to the configured content root. It is independent of the authoring tool and never exposes the author's absolute filesystem path.

The node union is explicit and closed for each schema version:

```ts
export type BlockNode =
  | ParagraphNode
  | HeadingNode
  | CodeBlockNode
  | ListNode
  | BlockQuoteNode
  | CalloutNode
  | TableNode
  | ThematicBreakNode
  | MathBlockNode
  | EmbedNode
  | ComponentNode;

export type InlineNode =
  | TextNode
  | EmphasisNode
  | StrongNode
  | DeleteNode
  | HighlightNode
  | InlineCodeNode
  | LinkNode
  | ImageNode
  | FootnoteReferenceNode
  | MathInlineNode
  | HardBreakNode;
```

Nodes contain only serializable data, child nodes, resolved identifiers, and optional logical source locations. They never contain functions, React elements, class names, or executable source.

## Component nodes

Body directives lower into component nodes:

```ts
export interface ComponentNode {
  type: "component";
  name: "hero" | "children" | "toc" | "section" | "columns" | /* ... */ string;
  props: Readonly<Record<string, JsonValue>>;
  children?: readonly BlockNode[];
  source?: SourceLocation;
}
```

Although the interface is serializable, the generated union should remain more specific than `string` where practical. For example, a generated `ChildrenComponentNode` can carry a validated `ChildrenProps` object. The generic representation is useful for schema files and compatibility fallbacks.

Rust applies defaults before generation. The TypeScript runtime receives normalized properties and does not repeat source-language validation.

## Embed nodes

Default visual embeds remain explicit component boundaries:

```ts
export interface EmbedNode {
  type: "embed";
  sourcePage: PageId;
  sourceFragment?: string;
  instanceId: string;
  mode: "embed" | "inline";
  showTitle: boolean;
  showSource: boolean;
  children: readonly BlockNode[];
}
```

For the first release, Rust expands resolved embed children into the host page's generated data while keeping provenance. This simplifies static rendering at the cost of some duplicated generated data. A future schema may deduplicate shared fragments, but it must not change authoring semantics.

## Manifest

`manifest.ts` contains site-wide information required before any page is rendered:

```ts
export interface SiteManifest {
  schemaVersion: number;
  site: {
    title: string;
    url: string;
    basePath: string;
    language: string;
    trailingSlash: boolean;
  };
  entryPage: PageId;
  routes: Readonly<Record<string, PageId>>;
  pages: readonly PageSummary[];
  tags: readonly TagRecord[];
  assets: readonly AssetRecord[];
}
```

`PageSummary` contains only data needed for route generation, collections, navigation, and metadata. Full body trees stay in page modules.

The route table must include `/` and every production route. Draft pages are omitted in production builds.

## Page modules

A generated page module follows this form:

```ts
import type { PageRecord } from "@mambosite/runtime";

const page = {
  schemaVersion: 1,
  id: "p_...",
  route: "/mambodot/commands/",
  sourcePath: "_mounts/mambodot/Commands.md",
  title: "Commands",
  listed: true,
  status: "published",
  tags: [],
  aliases: [],
  data: {},
  headings: [],
  body: [],
  children: [],
  outgoingLinks: [],
  backlinks: [],
  assets: [],
} as const satisfies PageRecord;

export default page;
```

The generator controls property order and formatting so diffs remain readable. Strings must be escaped as TypeScript literals safely. Generated source is formatted by the generator; running a general formatter must not be required for correctness.

## Page index

`pages/index.ts` provides a statically analyzable lookup for the web shell. The first implementation may use eager imports because both initial sites are small:

```ts
import pageA from "./p_a";
import pageB from "./p_b";

export const pagesById = {
  [pageA.id]: pageA,
  [pageB.id]: pageB,
} as const;
```

If the web runtime bundle becomes significant, code generation may switch to generated static import functions without changing Markdown or the page schema. Any lazy approach must remain compatible with static route generation.

## Navigation and search

`navigation.ts` stores the resolved route tree after `listed`, `order`, mounts, and hierarchy rules are applied. It should not require the runtime to reconstruct parent-child relationships.

`search.ts` is optional in the first milestone. When enabled, it contains pre-normalized records such as page ID, title, description, tags, headings, route, and plain searchable text. The compiler excludes comments, code when configured, and hidden metadata. A client-side search index may be constructed from these records by the web shell.

## Source locations

Production output may omit most source locations to reduce size. Development output should retain them so runtime errors and inspect tools can point back to Markdown. Source locations use normalized content-root-relative paths; absolute host paths are forbidden.

## Schema versioning

The compiler, generated modules, and runtime share an integer schema version.

- Compiler and runtime must fail clearly when their supported versions do not overlap.
- Additive optional fields may remain within a schema version when defaults are defined.
- Renamed fields, changed meanings, or node-union changes require a schema increment.
- Generated output records the compiler version for diagnostics, but builds must not use it as semantic input.

## Deterministic and atomic generation

For the same normalized inputs and configuration, generated bytes must be identical.

The writer must:

1. Sort pages, routes, tags, metadata keys, and assets deterministically.
2. Write into a temporary sibling directory.
3. Complete every file and asset successfully.
4. Replace the previous generated directory atomically where supported.
5. Remove stale generated files only inside the exact configured output directories.

No partial output is published after a compilation error.

## Deliberate exclusions

The generated layer does not contain:

- Raw Markdown requiring reparsing.
- Prebuilt React elements.
- Arbitrary HTML from authors.
- Site-specific CSS classes.
- Absolute filesystem paths.
- Network-fetched content.
- Nondeterministic timestamps in content modules.
- One generated `page.tsx` for every Markdown page.
